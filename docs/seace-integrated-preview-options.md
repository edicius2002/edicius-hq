# Integrated SEACE PDF preview: feasibility study

Date: 2026-11-12. Scope: the public Vercel web app on desktop and mobile, with the Raspberry Pi as an outbound-only worker. No Tailscale, Cloudflare domain, or inbound Pi port is assumed. This is a design study; no preview worker or Blob store has been deployed.

## What exists today

- The web obtains PDF links from `payload.documentUrl` and `payload.documents[].url` in [SeacePage.tsx](../apps/web/src/features/seace/SeacePage.tsx). Production previews `prod4.seace.gob.pe` through the authenticated Vercel Function in [document.ts](../api/seace/document.ts); `prod6.seace.gob.pe` opens the original for download because the Vercel fetch receives HTTP 403. The proxy in [documentProxy.ts](../api/seace/documentProxy.ts) allows only the two known numeric download paths, validates `%PDF-`, and caps the PDF at 20 MiB. The page accepts PDF links on any HTTPS `seace.gob.pe` subdomain, so the UI and proxy allowlists differ.
- A read-only count of Neon `production` on 2026-11-12 found 10,052 SEACE rows. There are 1,599 currently stored HTTPS document links: 972 `prod4` and 627 `prod6`, with no other stored URL host. The 1,175 process rows separately contain 3,970 document entries with a UUID but no URL or filename extension; these documents are not clickable in the current UI. They are **unclassified documents, not 3,970 known PDFs**. The UUID resolver in [server.py](../services/seace/vendor/seace_mcp/server.py) uses Alfresco and returns a short-lived URL, possibly on `alfprod.seace.gob.pe` or `prodcont2.seace.gob.pe`; it needs on-demand resolution and content classification before a process document can be offered as a PDF. The publisher's process payload shape is in [refresh.py](../services/seace/refresh.py).
- In a current sample, the Pi fetched one `prod6` PDF with HTTP 200 using the `node` user agent. The default `curl` agent received 403 on both the Pi and this PC. This verifies one route, not every document or long-term availability. Two sample PDFs measured 186,440 bytes (`prod6`, reported as `application/octet-stream` despite `%PDF-`) and 425,688 bytes (`prod4`, `application/pdf`). A separate process UUID resolved successfully on the Pi, but its download was a **13,981,918-byte ZIP** (`application/zip;charset=UTF-8`), not a PDF. A central-directory listing without extraction found two entries: one `.pdf` (14,663,456 expanded bytes) and one `.rar` (227,128 bytes). This supports a PDF-member preview path for this example while leaving the RAR as an original download; it does not establish the format distribution of the other UUIDs. The bytes and status were checked without displaying document URLs or database credentials.

## Approaches

| Approach                                                    | Coverage and user experience                                                                                                                                                          | Operational cost / blocker                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vercel-only, existing proxy                                 | `prod4` inline; direct download for `prod6`. Already deployed and needs no Pi.                                                                                                        | Vercel requests to `prod6` returned 403 in tested regions, so this does not provide reliable integrated preview for all PDFs. Another Vercel region is an experiment, not a guarantee.                                                                                           |
| Pi exposed on a public address                              | Potentially immediate streaming for `prod6` and Alfresco documents.                                                                                                                   | Requires externally reachable HTTPS, stable address and router/firewall work. This conflicts with the user's preference for no additional domain or tunnel and exposes a home service.                                                                                           |
| Pi outbound worker + Vercel Queues + private Blob           | Keeps the browser on the Vercel URL and Pi without inbound ports. Covers `prod6` after a brief wait; UUID process documents must be classified and only actual PDFs can be previewed. | Requires a continuously running Pi, Queue authentication boundary, Blob provisioning, polling and storage quota. ZIP inspection adds a separate safety and UX task. Must prove authenticated streaming PDF rendering on desktop/mobile; direct signed `iframe` remains optional. |
| Pi outbound worker + existing Neon job table + private Blob | Same PDF path, with small job metadata in Neon and no Queue OIDC renewal.                                                                                                             | Reuses the app's existing database but adds polling/writes to a Neon project that recently hit a storage allowance. It is a fallback if Vercel Queue authentication cannot be maintained safely. PDF bytes must never enter Neon.                                                |

### Recommended design to validate

Use **Vercel Queues + Vercel private Blob + an outbound Pi worker** for `prod6`, PDFs discovered through process UUID resolution, and `prod4` documents that exceed or fail the current proxy; keep the fast `prod4` proxy and original-link fallback. This uses only the existing Vercel project and Pi for new infrastructure. The Pi can fetch a sampled `prod6` PDF with the correct HTTP agent. Queue poll mode is designed for off-Vercel consumers. The Pi uploads through a signed Blob PUT; an authenticated Vercel Function streams the private PDF to the same-origin modal. Vercel states that streaming responses bypass its usual 4.5 MB response cap, but the route needs an actual large-PDF test. Prefer a narrow Vercel worker endpoint as the Queue credential boundary, subject to the Function-invocation budget; compare direct Queue polling if a safe OIDC renewal flow is proven. The UUID sample's ZIP means process coverage needs format classification and possibly a ZIP member picker, not a blanket PDF preview. These observations support feasibility, **not yet a working end-to-end preview**. [Queue poll mode](https://vercel.com/docs/queues/poll-mode), [private Blob delivery](https://vercel.com/docs/vercel-blob/private-storage), [streaming guidance](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions).

1. An authenticated Vercel endpoint checks the requested SEACE document against a server-side allowlist and the owner's visible record. It creates a short-lived, deduplicated Queue job with an opaque ID and document identifier. Do not place upload credentials in the job: they would expire while a job waits for an offline Pi. Do not log source URLs, signed URLs, OIDC tokens, or database credentials.
2. The Pi polls a protected Vercel worker endpoint using a credential scoped to this worker. That Function uses its Vercel OIDC token to receive a Queue lease and returns the document identifier, receipt handle, and fresh, path-specific signed Blob PUT URL. For stored `prod4`/`prod6` paths the Pi fetches the original; for process UUIDs it first resolves a fresh Alfresco download URL, then validates the resulting host. It enforces no redirects to unapproved hosts, timeouts, bounded concurrency, size limits, and magic-byte/type classification. A `%PDF-` response is uploaded as `application/pdf`. A ZIP is not mislabeled as PDF: either inspect its entries safely and offer validated PDF members individually or retain only the original ZIP download. Other formats remain original downloads. After successful upload the Pi calls the protected endpoint to acknowledge the lease; failures remain eligible for retry. [Queue API receive/ack](https://vercel.com/docs/queues/api), [signed PUT constraints](https://vercel.com/docs/vercel-blob/vercel-signed-urls), [Python ZIP security notes](https://docs.python.org/3/library/zipfile.html).
3. The modal polls a small authenticated status endpoint. Once the immutable Blob path exists, the same-origin `/api/seace/preview-file` route checks the session and streams the private Blob with `Content-Type: application/pdf`, `Content-Disposition: inline`, and private/no-store caching. This avoids cross-origin `iframe` and CORS dependencies. As an optional cost/latency optimization, Vercel can issue a short-lived GET-only signed URL for the exact path, but it must not replace the streaming route until a real private signed PDF is verified in an `iframe` on desktop and mobile. Signed URLs are bearer capabilities while valid and must not appear in logs. If native PDF display fails on a target browser, evaluate PDF.js against the same-origin route, including memory use and range requests. [Private Blob stream example](https://vercel.com/docs/vercel-blob/private-storage), [signed URL embedding](https://vercel.com/docs/vercel-blob/vercel-signed-urls), [Vercel issue #591](https://github.com/vercel/storage/issues/591#issuecomment-1936302019).
4. Blob objects receive a one-day TTL and explicit deletion after the useful window where possible. The UI shows bounded progress and offers the original document immediately when the Pi is offline, quota is exhausted, SEACE denies access, the PDF is unsupported, or the wait budget expires. [Blob TTL](https://vercel.com/docs/vercel-blob/using-blob-sdk#expire-blobs-automatically), [Blob Hobby limits](https://vercel.com/docs/vercel-blob/usage-and-pricing).

## Gates before implementation and release

1. **Queue authentication spike:** prove that a Pi-authenticated Vercel worker endpoint can receive and acknowledge Queue leases safely, without handing the Vercel OIDC token to the Pi. Check actual Function invocation usage against the 10-second polling budget. Alternatively prove unattended, production-scoped Queue OIDC renewal on the Pi. If neither is safe or within quota, use the existing Neon metadata queue; never leave an expiring token on the Pi.
2. **Blob and display proof:** create a private test store, upload one non-sensitive PDF from the Pi using a path-scoped signed PUT, then serve it through an authenticated same-origin streaming route. Verify inline rendering on desktop and mobile with both a small PDF and one larger than 4.5 MB (the sampled process PDF is about 14.7 MB expanded). Verify response headers, true streaming, cache, TTL, deletion, and range behavior. Separately test whether a private signed GET actually lacks `X-Frame-Options: DENY` and can render in an `iframe`; inspect CORS before considering `fetch` to a `blob:` URL. Direct signed display is not a release dependency.
3. **Coverage proof:** sample `prod4`, `prod6`, and a representative set of UUID-resolved process documents. Record success/failure, verified magic bytes, MIME, size distribution, PDF/ZIP/other counts, and time from click to first page. The 3,970 process UUID entries require UI and resolver work beyond switching the current links. For ZIPs, test safe entry listing and bounded extraction of PDF members; do not assume a ZIP contains a PDF.
4. **Quota and failure proof:** exercise Pi offline/restart, duplicate delivery, expired signed URLs, SEACE 403, oversized/non-PDF response, malicious or oversized ZIP entries, Queue and Blob allowance exhaustion. Keep direct original links visible in every failure state.

No production service, Blob store, or Queue was created by this study.
