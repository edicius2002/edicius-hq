# Opciones para acelerar la visualización de PDF de SEACE

Fecha: 7 de noviembre de 2026. Investigación de fuentes primarias; este documento no cambia el visor.

## Cuello de botella actual

`services/api/app/routers/seace_documents.py` lee y valida **todo** el PDF remoto antes de responder. Después, `apps/web/src/features/seace/data.ts` llama a `response.blob()` y `SeacePage.tsx` crea un `blob:` URL para el iframe. [`Response.blob()` lee la respuesta hasta completarla](https://developer.mozilla.org/en-US/docs/Web/API/Response/blob); por ello, aunque el modal se abra enseguida, el navegador no recibe la URL del PDF hasta terminar las dos transferencias (SEACE → API → navegador). La precarga introducida en esta rama esconde parte de esa espera cuando el usuario mantiene el cursor o foco sobre el enlace; las [mediciones existentes](seace-preview-performance.md) no incluyen el pintado del iframe.

## Opciones y coste

| Opción                              | Qué adelanta o reduce                                                                                                                 | Límite principal                                                                                                                             | Prioridad                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Medir las fases en navegador y API  | Distingue espera de SEACE, envío al navegador y pintado                                                                               | Requiere instrumentación temporal                                                                                                            | Primera                                           |
| Proxy con respuesta en streaming    | Solapa el traslado SEACE → API y API → navegador; reduce la espera hasta el primer byte y el uso de memoria del API                   | El `blob()` actual seguiría esperando el archivo completo para mostrarlo; el control de errores y tamaño se complica después del primer byte | Prototipo acotado                                 |
| PDF.js con `url` y `httpHeaders`    | Puede solicitar el PDF autenticado y usar streaming/rangos, pintando la primera página sin esperar necesariamente el archivo completo | Suma visor/worker propios; el beneficio depende de la estructura del PDF y de la latencia/cadencia de SEACE                                  | Solo si la medición muestra que el pintado domina |
| Imagen o texto de la primera página | Entrega una vista ligera si se genera y guarda **antes** del clic                                                                     | Si se genera tras el clic, el servidor debe descargar el PDF y convertirlo primero; no elimina la espera de origen                           | Útil como vista previa preparada                  |
| Caché corta por documento           | Evita repetir la descarga de SEACE al reabrir el mismo PDF                                                                            | La respuesta actual usa `Cache-Control: no-store`; un cambio requiere política de caducidad y privacidad                                     | Evaluar con métricas de reapertura                |

[`StreamingResponse`](https://www.starlette.io/responses/) puede enviar un generador de bytes. Aunque el `blob()` actual seguiría esperando el último byte para crear la URL del iframe, el API podría enviar los primeros bytes al navegador antes de terminar la descarga desde SEACE y acortar el tiempo total. Mostrar la primera página antes del último byte sí exigiría un visor capaz de consumir la respuesta progresivamente. La ruta actual exige un bearer token en `Authorization`; un iframe apuntando directamente al endpoint no envía ese encabezado. [PDF.js `getDocument`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html) permite `url`, `httpHeaders`, `disableStream`, `disableRange` y `rangeChunkSize`, y usa Fetch/XHR sujeto a CORS. Es una alternativa técnica para un visor propio autenticado, que debe probarse antes de reemplazar el visor nativo.

Las solicitudes HTTP `Range` permiten obtener partes del archivo y responden con `206` si el servidor las admite ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)). Pero una solicitud por rango adicional tiene latencia propia. En el prototipo previo con el PDF prod6 `433954`, PDF.js necesitó 11 rangos de 64 KiB (831.337 bytes) para preparar la primera página; respetar 1,1 s entre inicios llevó unos 11,6 s, mientras el PDF completo tardó alrededor de 2 s. Esa muestra descarta los rangos pequeños como mejora inmediata para ese archivo. Un [PDF linealizado](https://pdfa.org/glossary-of-pdf-terms/) sí está organizado para mostrar la primera página antes de terminar la descarga; el PDF `433954` no tiene cabecera de linealización. No se ha comprobado el resto del catálogo.

## Prueba de primera página en un PDF real

El documento prod6 `433954` tiene 7 páginas y pesa 2.338.665 bytes. En una descarga medida aquí tardó 2.251 ms. Las seis primeras páginas no dieron texto extraíble; la última dio 277 caracteres. Por tanto, una ficha de texto de ese documento requeriría OCR para la mayor parte del contenido. La primera página contiene una imagen JPEG incrustada de 294.201 bytes, extraíble en aproximadamente 1 ms **después** de descargar y abrir el PDF. Renderizarla a 749 × 1.065 píxeles y codificarla como JPEG de calidad 75 produjo 117.506 bytes; la rasterización tardó 27 ms y la codificación 105 ms. Es una vista rápida potencial, pero no ahorra la espera de origen si se crea al hacer clic.

## ¿Serviría “scrapear” el PDF?

Extraer texto no evita obtener los bytes del PDF remoto: el extractor necesita el documento fuente. Si se hace bajo demanda, agrega análisis después de la descarga. Además, el texto puede salir fuera de orden o faltar en un PDF escaneado; en este último caso se necesita OCR ([documentación de PyMuPDF](https://pymupdf.readthedocs.io/en/latest/recipes-common-issues-and-their-solutions.html)). Tampoco reproduce tablas, sellos, firmas o el diseño con fidelidad.

La extracción sí podría servir para una **ficha resumida** generada previamente por el colector, mientras el PDF original permanece disponible para verificarlo. Para una miniatura visual, [PyMuPDF puede renderizar una página a imagen](https://pymupdf.readthedocs.io/en/latest/page.html#Page.get_pixmap), aunque introducirlo en el servicio requiere revisar su [licencia AGPL/comercial](https://pymupdf.readthedocs.io/en/latest/about.html#license-and-copyright). Una miniatura preparada antes del clic puede dar respuesta inmediata; renderizarla bajo demanda no mejora la latencia de origen.

## Siguiente experimento recomendado

Registrar, en 10 aperturas de PDF pequeños y grandes, estos cuatro hitos: inicio de solicitud a SEACE, primer byte de SEACE, último byte del API, y primera página legible en el navegador. Separar clic inmediato de clic tras precarga. Si el último byte llega pronto y el iframe tarda, evaluar un visor de primera página; si la espera está antes del último byte, priorizar streaming o una vista previa preparada. La cabecera actual `no-store` impide reutilizar una respuesta HTTP guardada ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)); medir aperturas repetidas antes de cambiarla.
