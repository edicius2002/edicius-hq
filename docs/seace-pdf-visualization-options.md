# Options for faster SEACE PDF previews

Date: November 7, 2026. This research uses primary sources and does not change the viewer.

## Current bottleneck

`services/api/app/routers/seace_documents.py` reads and validates the entire upstream PDF before responding. Then `apps/web/src/features/seace/data.ts` calls `response.blob()`, and `SeacePage.tsx` creates a `blob:` URL for the iframe. [`Response.blob()` reads the response to completion](https://developer.mozilla.org/en-US/docs/Web/API/Response/blob). The modal opens immediately, but the iframe does not receive a PDF URL until both transfers finish: SEACE to API, then API to browser. The bounded prefetch in this branch hides some of the wait when the user hovers or focuses a link; the [earlier measurements](seace-preview-performance.md) do not include iframe rendering.

## Options and costs

| Option                              | Potential benefit                                                                                     | Main limitation                                                                                                 | Priority                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Measure each phase                  | Separates upstream wait, browser transfer, and viewer load                                            | Needs temporary instrumentation                                                                                 | First                                                     |
| Stream the proxy response           | Overlaps the SEACE-to-API and API-to-browser transfers; reduces time to first byte and API memory use | The current `blob()` still waits for the whole file; size and error handling become harder after the first byte | Limited prototype                                         |
| PDF.js with `url` and `httpHeaders` | Can fetch the gated endpoint and use streaming or byte ranges                                         | Adds a viewer and worker; results depend on PDF structure and SEACE latency                                     | Only if measurement shows that viewer rendering dominates |
| First-page image or text            | Gives a light preview if prepared and stored before the click                                         | Creating it after the click still requires downloading and processing the PDF                                   | Useful when prepared beforehand                           |
| Short-lived document cache          | Avoids another SEACE download when reopening the same PDF                                             | Current `Cache-Control: no-store` prevents HTTP reuse; expiry and privacy need a policy                         | Evaluate after measuring reopens                          |

[`StreamingResponse`](https://www.starlette.io/responses/) can send an iterator of bytes. Even though the current `blob()` still waits for the last byte before creating the iframe URL, the API could send bytes to the browser while it continues downloading from SEACE. Showing the first page before the last byte requires a viewer that consumes the response incrementally. The current endpoint requires an `Authorization` bearer token, which a plain iframe URL cannot attach. [PDF.js `getDocument`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html) supports `url`, `httpHeaders`, `disableStream`, `disableRange`, and `rangeChunkSize`, subject to browser CORS rules. An authenticated PDF.js viewer would need a measured prototype before replacing the native viewer.

HTTP `Range` requests can fetch part of a file and receive `206` when supported ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)). Each additional request also incurs latency. In the earlier prototype with prod6 PDF `433954`, PDF.js needed eleven 64 KiB ranges (831,337 bytes) to prepare the first page. Pacing starts 1.1 seconds apart took about 11.6 seconds, while fetching the full PDF took about 2 seconds. Small ranges are therefore a poor immediate choice for that sample. A [linearized PDF](https://pdfa.org/glossary-of-pdf-terms/) is organized to display its first page before the full download finishes; PDF `433954` has no linearization header. The rest of the catalog was not checked.

## Would extracting content help?

On-demand text extraction does not avoid fetching the upstream PDF. It adds processing after that fetch and may miss text in scanned pages, which require OCR ([PyMuPDF documentation](https://pymupdf.readthedocs.io/en/latest/recipes-common-issues-and-their-solutions.html)). Extracted text also does not faithfully preserve tables, stamps, signatures, or layout. A summary prepared in advance could complement the original PDF.

For a visual thumbnail, [PyMuPDF can render a page to an image](https://pymupdf.readthedocs.io/en/latest/page.html#Page.get_pixmap), though adding it to the service requires reviewing its [AGPL/commercial license](https://pymupdf.readthedocs.io/en/latest/about.html#license-and-copyright). A thumbnail prepared before the click can appear promptly; creating it on demand does not remove upstream latency. In one measured prod6 PDF (`433954`, seven pages, 2,338,665 bytes), the first six pages yielded no extractable text. Its first page contained an embedded 294,201-byte JPEG, extractable in about 1 ms **after** downloading and opening the PDF. Rendering it at 749 × 1,065 pixels as a quality-75 JPEG yielded 117,506 bytes and took 132 ms for rasterization and encoding, after a 2,251 ms download.

## Follow-up measurements

The [streaming and browser benchmark](seace-pdf-visualization-benchmark.md) found a much earlier first byte with streaming, but only a 70 ms difference in full download time over the local connection. Two clicks without prefetch took 2.79 and 3.24 seconds to the iframe `load` event; once the `blob:` URL existed, that event followed in 19–57 ms. These samples favor retaining the native viewer and bounded prefetch. The `no-store` header prevents reuse of a stored HTTP response ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)); measure how often users reopen the same document before changing it. If the app is used over a slow remote connection, repeat the streaming comparison from that client.
